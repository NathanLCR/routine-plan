Focus

Direct continuation of W6–W7's transfer-learning thread, now framed entirely as a CA1 execution recipe. The spine: pick a real dataset → find which two off-the-shelf backbones already work on it (use AI to do the literature review for you) → build your customised head on the better one → tune it the cheap way (one hyperparameter at a time, simplest model that works) → read the validation curve, not training → use EarlyStopping to stop at the right epoch → keep records of every experiment so you can defend the result, even if your custom model ends up worse than the base. Key Concepts

  • The CA1 recipe (start to finish) — (1) locate the dataset, ideally with a Hugging Face link; (2) prompt an LLM with the dataset + the list of CNN architectures to find the two most appropriate, easy-to-use models and what accuracy prior papers reported; (3) apply both, compare; (4) build your customised model on top of the better one.
  • Use AI as an assistant, not the author — let ChatGPT do the literature review (which models were used on this dataset, best reported values) and propose layer structure. You still run, tune, and justify. (AI-use stays within the assignment's allowed level.)
  • Two-then-customise — apply exactly two base models (not all 22 in the zoo) + your customisation. The customised model on top of the best base is your model — that's the assessed contribution.
  • Transfer learning = the basis of customisation — in ~99% of cases a customised model is built on a base model via transfer learning. The base brings pre-trained weights (e.g. VGG16 trained on ImageNet); you bolt a head on top.
  • Base model is not mandatory, but strongly preferred — you can build fully from scratch, but it needs far more fine-tuning to reach a target accuracy. Analogy: building on a base is like having a foundation/frame for a shed already in place — you reach the target value sooner.
  • Benchmark/base datasets — ImageNet is the default pre-training set, but others exist; the pre-trained weights you import reflect whatever benchmark the backbone was trained on.
  • Trainable vs non-trainable weights — layer.trainable = False (preferred): don't update the transferred weights → lower compute, more efficient. = True: a huge number of parameters get trained → slow (the epochs balloon). Default to freezing.
  • "Block" terminology — a block = a repeated combination of conv layer(s) + max pooling. VGG16 = ~5 such blocks (conv → conv → maxpool, repeated). Everything up to the end of those blocks is the base; from there on is your customisation.
  • The head is just an ANN — after the conv/pool blocks, the dense part (Dense → … → Dense(softmax)) is a normal fully-connected ANN. In CNN context it's called the fully-connected / dense layers. No convolution appears in your head's summary — the conv stack lives in the frozen base.
  • Output layer is fixed by the problem — number of output nodes = number of classes; activation = softmax (multi-class) or sigmoid (binary). Little flexibility here — don't try to "tune" it.
  • Tuning logic for the head (the key message) — start with ONE hidden layer, activation relu, one width to play with. Pick a power-of-two width (lecturer's preference: 64). Run, read accuracy, then optimise.
  • Hyperparameter sweep on width — try 2**i for i in 5..10 → 64, 128, 256, 512, 1024. Allowed, because runtime explodes (a run can take 4+ hours), so you sweep deliberately.
  • When to add a second hidden layer — only if adding it actually improves accuracy. If 128 helped, try stepping 128 → 256, etc. If a new layer gives no significant improvement, remove it and keep the simpler model.
  • "10% improvement over the base is acceptable/reasonable." — you don't need miracles; a modest, defensible gain on top of the base is a good CA result.
  • GlobalAveragePooling2D — common between base and head: averages each filter's values, collapsing spatial dimensions → fewer parameters → faster. Not fundamental; can be removed, but it's a cheap efficiency win.
  • Max pooling = down-sampling — slides a 2×2 window over the matrix, keeps the max of each 4 values → a 32×32 image becomes 16×16. Halves height and width → big efficiency gain. (Stride/padding belong to conv + pooling, not to dense layers.)
  • Dropout (the regulariser to add before more layers) — Dropout(0.5) randomly turns off ~50% of connections during training to curb overfitting. Cheaper than adding capacity.
  • Why dense layers get heavy — the weight count — connections between two dense layers ≈ (nodes_prev + 1) × nodes_next (the +1 is bias). e.g. 256 → 128 ≈ 257 × 128 weights. Two big dense layers make the model very heavy (a 2-hour run can become 5–6 hours). Don't add layers/width without a reason.
  • Reading the loss/epoch curve — watch VALIDATION — training loss keeps dropping with more epochs (misleading). For evaluation, look at the validation curve: it falls, bottoms out (e.g. ~epoch 20), then rises again (overfitting). Select the epoch at the validation minimum, not the last epoch.
  • EarlyStopping = patience — let it run; after N (e.g. 5) epochs with no improvement (or worsening), it stops and rolls back. Controls overfitting and runtime — counts as a form of hyperparameter optimisation. Pair with ModelCheckpoint to save the best weights. monitor='val_loss', patience=5.
  • Augmentation matters too — data prep itself is a tuning surface: how many augmented images per original (5? 50?), rotation range, etc. If you already have plenty of varied images per class, you may not need heavy augmentation — but if you use it, have a reason ("why did you add it?" is a fair exam question).
  • It's OK if the custom model loses to the base — sometimes no amount of tuning beats the base model. That's a valid result if you can explain why and show the experiments (changed layers, widths, activations, etc.). Keep all records.
  • Model selection metrics — compare on accuracy/loss + (when relevant) per-class metrics, and also factor in training time (transfer-learning efficiency). The best model balances accuracy and cost.

Notes (live capture — recorded CNN/CA1 half)

The end-to-end CA1 play (lecturer, "if I were you guys"):

  • Locate the dataset first; get a Hugging Face link if possible. If not downloadable, assemble your own image folders and upload them.
  • Prompt an LLM: paste the architecture list, ask for the two most appropriate, easy-to-use models for this dataset, and ask which models prior researchers used + their best reported accuracy → that's your literature review, done for you.
  • Apply the two recommended models (e.g. it might return something like a Vision/EfficientNet-type model + a MobileNet variant). Get each one's structure (layer count, etc.), run on your data, record accuracy.
  • Example outcome: Model 1 → 71%, Model 2 → 65%. Keep the better one (71%) and build your customised model on top of it.
  • Low accuracy can happen — if a model lands near 50% it's basically a coin flip; change the base/approach.

Custom-model question — must you use a base model?

  • No, but transfer-learning-based customisation usually performs better and gets you to target accuracy sooner. From scratch = much more fine-tuning. Not "written in stone," just the efficient default.

Trainable flag:

  • trainable = True → updates the base's transferred weights and your params → huge parameter count, very slow over the epoch budget.
  • trainable = False → freeze base, train only the head → preferred (lower compute).

Anatomy of the VGG16 summary:

  • Input layer = images. Then repeated conv → conv → maxpool blocks (×5). Each conv+pool group is a "block."
  • Everything up to the last block = VGG16 base. From there = your customisation (the dense head).
  • Your head ≈ two hidden dense layers + output. Output is fixed (num classes, softmax) — little to tune there.

The tuning method (the heart of the session):

  • Start with one hidden dense layer, relu, width 64. Run → read accuracy.
  • Sweep width over powers of two: 64 → 128 → 256 → 512 → 1024 (2**i, i=5..10). Each run can take hours, so sweep on purpose.
  • Add a second hidden layer only if it improves things; if no significant gain, remove it. Prefer the simpler model.
  • Other knobs if needed: activation function, an extra conv + maxpool layer (with stride/padding), GlobalAveragePooling, Dropout(0.5), or even swapping the base.
  • A ~10% lift over the base is a reasonable, defensible CA result.

Why dense layers are expensive:

  • Weights between layers ≈ (prev_nodes + 1) × next_nodes. 256 → 128 ≈ 257 × 128. Two wide dense layers make the model very heavy; dropout halves active connections to relieve this. Don't stack capacity without justification.

Max pooling explained (student Q):

  • It's down-sampling: 2×2 window over the image matrix, keep the max per window → 32×32 → 16×16. Halves H and W → faster model. input_shape=(32,32,3) is just the image dimensions (H, W, channels) set during preprocessing; resize there if needed.

Reading the curves + EarlyStopping (student Q on metrics):

  • Training loss always decreases with epochs — don't be fooled. Evaluate on the validation curve.
  • Validation loss falls, hits a minimum (~epoch 20 in the example), then climbs (overfitting). Choose the validation-minimum epoch.
  • If the full run is 100 epochs / 5 hours but the best is at epoch 20, use EarlyStopping(monitor='val_loss', patience=5) + ModelCheckpoint to stop early and save the best weights. Code is in one of the course notebooks.

"What if ResNet (81%) beats VGG16 (71%) beats simple CNN (65%)?" (student Q):

  • Then build your customised model on top of the best base (ResNet here) — that becomes your model.
  • If tuning can't beat the base, that's still a presentable result: state it, show why, and show your optimisation experiments. Keep the records.

Augmentation as a tuning surface:

  • Decide augmented-images-per-original (e.g. +5 vs +50), rotation range (recall RandomRotation ~30°), etc. — all affect results.
  • If you already have enough varied images per class/object, you may not need much. But if you use augmentation in class, be ready to justify why.

Supplementary: RNN architecture & why RNNs beat traditional models for forecasting

> NOT RECORDED. The lecturer covered this in the unrecorded second half. The following is an accurate explainer to fill the gap — confirm specifics (notation, examples) against the slides. This is the natural bridge from CNNs (spatial data) to RNNs (sequential/temporal data), and connects to the NLP-W5 RNN intro note.

The core problem RNNs solve

A standard MLP/ANN (and a CNN) assumes inputs are independent and of fixed size. Forecasting and language are neither: the value at time t depends on what came before, and sequences vary in length. RNNs add a hidden state that is carried forward step by step, giving the network a form of memory of the past.

How an RNN works (one equation, conceptually)

At each timestep t the network combines the current input x_t with the previous hidden state h_{t-1}:

h_t = activation(W_x · x_t + W_h · h_{t-1} + b)
y_t = W_y · h_t + b_y

The same weights (W_x, W_h, W_y) are reused at every timestep — this weight sharing across time is the RNN analogue of a CNN's filter sharing across space. Training uses backpropagation through time (BPTT): the network is unrolled across the sequence and gradients flow backward through every step.

Why RNNs beat traditional forecasting models

  • Memory of arbitrary past context — classical models (ARIMA, exponential smoothing, linear/MLP regressors on lagged features) only see a fixed, hand-chosen lag window. An RNN's hidden state can, in principle, carry information from far earlier in the sequence without you pre-specifying the lags.
  • Variable-length sequences — RNNs process sequences of any length with the same parameters; an MLP needs a fixed-size input vector, so you'd have to fix and engineer the window manually.
  • Learned temporal features, not hand-crafted ones — ARIMA assumes (roughly) linear, stationary structure and needs differencing/manual order selection. RNNs learn non-linear temporal dependencies directly from data.
  • Shared parameters across time — far fewer parameters than a dense net that takes the whole window as a flat input, and it generalises across positions in the sequence.
  • Naturally multi-step / seq-to-seq — RNNs extend cleanly to multi-output forecasting and encoder–decoder setups, whereas classical methods get awkward beyond one-step-ahead.

The catch (and the fix)

Vanilla RNNs suffer from vanishing/exploding gradients over long sequences, so they struggle to learn long-range dependencies. The standard fixes are gated variants — LSTM and GRU — which add gates to control what the hidden state keeps, forgets, and outputs. Expect these next.

When traditional models still win

For short, strongly seasonal/stationary series with little data, ARIMA / exponential smoothing are often as good or better and far cheaper to fit and interpret. RNNs (and LSTMs) pay off with longer, non-linear, multivariate sequences and enough data to train on. Forecasting competitions (e.g. M-series) have repeatedly shown simple statistical baselines are hard to beat — so a good forecasting CA compares against them rather than assuming deep learning wins.
